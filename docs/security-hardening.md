# Безопасность ядра 0.6.0

## Граница доверия

Этот документ описывает прежний SQL runtime, доступный теперь только через явный `WMS_DATABASE_PROFILE=legacy`. Новый запуск по умолчанию использует [hardened-v1](security-hardened-profile.md): отдельные logins, ограничение склада и подписанный контекст пользователя. Порядок установки и grants этих профилей различается.

HTTP-клиент проходит OIDC и проверку прав склада/владельца. SQL login backend остаётся доверенной сервисной учётной записью: контрактные представления доступны ей целиком, actor_id передаёт аутентифицированный host. Этот login нельзя выдавать конечным пользователям. Полной изоляции при краже сервисных credentials эти изменения не обещают. Владелец схемы, установщик и код compiled-модулей остаются доверенными.

Runtime не должен владеть объектами, создавать объекты или напрямую менять таблицы в схемах ядра и `mod_*`. Preflight запрещает владение самой базой и специальные роли чтения/записи файлов сервера, запуска программ и административного управления. Проверяются и SET ROLE, и наследуемые привилегии, даже когда SET запрещён. Интеграциям нужны отдельные минимальные роли. Произвольный сторонний Go-код внутри процесса не изолирован.

## Обязательные guards

Миграция 0006 сохраняет привязки активируемых модулей в `platform.required_guards`. Отключение модуля и удаление guard из manifest не удаляют требования. Изменить требования может владелец установки. DELETE пакета считается явной административной деинсталляцией и удаляет его требования; перед ней нужно оценить бизнес-последствия.

Резерв, ручное освобождение и движение проверяют требования в PostgreSQL под блокировкой документа. Прямой SQL-вызов проходит ту же защиту. Нет guard, модуль disabled или нарушена привязка — операция откатывается. Compiled guard должен иметь установленную SQL-реализацию `(uuid line, uuid actor) RETURNS void`, зарегистрированную владельцем в `platform.sql_guards`. Без SQL-реализации startup отклоняется. SQL — единственный исполнитель бизнес-проверки. Host больше не вызывает Go-guards перед проведением. Штатные Go-пакеты содержат только привязки/валидацию; SQLOnlyGuard запрещает локально выдавать разрешение. Таким образом, API и прямой kernel SQL используют один предикат, а не две реализации.

Host сверяет executable-проекцию manifest при старте и перед новой командой. Изменения конфигурации сериализованы с командами. Старый процесс после изменения политики прекращает новые записи до согласованного перезапуска. Повтор завершённой команды возвращает сохранённый результат без повторного проведения и проверки текущих guards. `WMS_REQUIRED_MODULES` добавляет требования, но пустое значение не отменяет требования БД.

## Правила без отдельной Go-сборки

Runtime `declarative_v1` поддерживает проверки строковых полей JSON: `eq`, `nonempty`, `future` (RFC3339), `not_actor`. Условия соединяются AND. Неизвестные операции и поля описания правила отклоняются host. На policy допускается 1–32 условия; на модуль — до 32 policies. Нет SQL/eval/сетевых вызовов.

Пример элемента `policies`:

```json
{"handler":"AllowDispatch","conditions":[{"field":"decision","op":"eq","value":"approved"},{"field":"expires_at","op":"future"}]}
```

Manifest связывает handler с обязательной точкой через `guards`, задаёт собственную `mod_*` схему, target_schema_version и ID/SHA256 миграций. Read contract: `mod_<id>.document_facts_v1(organization_id, warehouse_id, document_id, content_revision, payload)`. Отсутствующие, неоднозначные и устаревшие факты запрещают команду. View должны читать runtime и владелец kernel-функций. Изменения фактов обязаны блокировать тот же документ; пример качества обеспечивает это trigger-функцией. Разработчик пакета отвечает за этот протокол своих таблиц.

Host валидирует форму и совместимость пакета; правила исполняет только PostgreSQL. Пакет можно установить в общий binary без Go-пересборки; после активации нужен перезапуск host. Произвольные алгоритмы этим DSL не выражаются: для них остаётся доверенный compiled-пакет с SQL-guard. Горячая загрузка стороннего кода не реализована.

## Declarative v2: альтернативы и типизированные факты

`declarative_v2` требует ядро 0.5.0. Policy содержит `handler` и `any`: достаточно одной группы; внутри группы все `conditions` обязательны. До 16 групп, до 32 условий в группе, не более 128 условий суммарно на policy; до 32 policies, размер каждой до 16 KiB. Неподдерживаемые поля/операторы и превышение границ отклоняются.

```json
{"handler":"Allow","any":[{"conditions":[{"field":"zone","op":"in","values":["cold","dry"]},{"field":"weight","op":"decimal_lte","value":"1200.50"}]},{"conditions":[{"field":"override","op":"is_true"},{"field":"evidence","op":"exists"}]}]}
```

Операторы: строковые `eq`, `neq`, `in`, `nonempty`, `future`, `not_actor`; `is_true` требует JSON boolean true, `exists` — присутствующее не-null поле. `decimal_gte`/`decimal_lte` сравнивают десятичные строки через PostgreSQL numeric, без float64: максимум 128 ASCII-символов, без экспоненты, NaN/Infinity и ведущего плюса. Список `in` содержит 1–64 строки длиной до 1024 байт. Неверный тип/отсутствие факта даёт false для соответствующей группы. Отсутствующая, неоднозначная или устаревшая строка facts запрещает всю проверку. v1 сохраняет прежнюю SQL-семантику.

Это расширение предикатов, а не готовая платформа произвольных workflows. Свои схемы фактов и SQL projections устанавливаются доверенным пакетом. GUI редактора правил, модульные маршруты, процессные автоматы и sandbox стороннего кода пока отсутствуют. Обновление модуля требует управляемой активации и перезапуска.

## Контроль качества 1.2.0

Миграция `003_authoritative_guard.sql` добавляет действующую политику организации/склада и SQL-guard отгрузки. Нужны последняя запись approved, совпадение content_revision и policy_revision, срок в будущем, evidence_reference длиной 8–2048 символов после обрезки пробелов и отдельный reviewer с актуальным `quality.approve` на нужном складе/владельце. Автор отгрузки не может подтвердить её сам. При отсутствии политики отгрузка запрещена.

Записи решений блокируют документ через SECURITY DEFINER trigger с фиксированным search_path. Отзыв решения и отгрузка получают определённый порядок. Смена политики и отзыв reviewer grant сериализованы с SQL-проверкой. Решения остаются append-only.

Проверяется ссылка на доказательство, а не существование/подлинность байтов. API записи решений, хранение вложений и UI ещё нужны. Учётная запись, которой разрешена запись решений, отвечает за аутентификацию reviewer: имя в строке само по себе не доказывает авторство.

## Истечение резервов

Обязательный worker независимо от relay вызывает `inventory.expire_reservations(100)`. После неполной пачки ждёт секунду, после полной сразу продолжает. Пачка блокирует документы через SKIP LOCKED, затем строки, остатки и резервы. Повторная проверка под блокировкой предотвращает двойное освобождение. В одной транзакции обновляются резерв, счётчики документа/остатка, версии, история, аудит и outbox. Работает и для закрытого документа. Изменение content_revision аннулирует прежние согласования.

Автоматическое освобождение не вызывает клиентский release guard: истёкший резерв освобождается независимо от бизнес-согласований. Физический остаток не меняется. Системный actor с issuer `wms:system` не является OIDC-пользователем.

Истечение асинхронно: до успешной обработки резерв удерживает доступное количество. При блокировках и большой очереди задержка может превышать секунду; отгрузка по истёкшему резерву запрещена. Простой процессов останавливает фоновые задачи. Нужен мониторинг возраста просроченных резервов и ошибок worker. `/readyz` проверяет БД; состояние фоновой обработки опубликовано независимо (см. ниже).

## Доставка outbox

Для запуска обязательны `WMS_OUTBOX_URL` и `WMS_OUTBOX_HMAC_KEY`: фиксированный HTTPS ingress брокера и base64 минимум 32 случайных байтов из secret manager. Все экземпляры установки используют один ingress и согласованный ключ. Маршрутизацию и fan-out подписчикам выполняет брокер. `subscribers` внутри module manifest пока не исполняются.

Событие арендуется на 30 секунд с новым UUID-токеном. Сетевой вызов ограничен 5 секундами и проходит после закрытия транзакции claim. Подтверждение проверяет токен и срок. Устаревший worker не может изменить результат новой аренды. После сбоя применяется экспоненциальная задержка; после 12 неуспешных подтверждений — dead state. При гибели worker событие доступно после окончания аренды.

Доставка — at-least-once. Получатель сохраняет событие долговечно перед 2xx и дедуплицирует `X-WMS-Event-ID`. Возможен повтор после принятия события и потери ответа/ack. Глобальный порядок и exactly-once не обещаются. Ошибки журналируются без payload/ключей/URL. Состояние видно в `contracts_v1.outbox_health`; нужны оповещения на dead>0 и возраст backlog. UI управления dead-letter пока нет; восстановление выполняет администратор после устранения причины, сохраняя event ID.

`X-WMS-Signature` — hex HMAC-SHA256 от `timestamp + "\n" + event_id + "\n" + exact_body`. Timestamp передаётся в `X-WMS-Timestamp` (Unix seconds). Получатель проверяет подпись constant-time, окно времени и дедупликацию. Ключ не передаётся в URL.

Redirect, URL credentials/query/fragment и proxy из окружения запрещены. DNS-адреса проверяются перед новым соединением; loopback, link-local, metadata и служебные диапазоны запрещены. `WMS_OUTBOX_ALLOW_PRIVATE=true` разрешает частные unicast-адреса брокера для on-premises, сохраняя запрет loopback/link-local. TLS сертификат проверяется стандартным механизмом.

## Пропускная способность и контроль фоновой работы

Relay пакетно арендует столько событий, сколько сейчас свободно отправителей. `WMS_OUTBOX_CONCURRENCY` — 1–64, по умолчанию 16. Завершивший доставку слот сразу получает новую работу; медленный запрос удерживает только свой слот. Непустая очередь обрабатывается непрерывно; ожидание 100 мс используется после пустого claim/ошибки. Максимум одновременно арендованных этим процессом событий равен числу слотов. Несколько процессов распределяют события через SKIP LOCKED; глобальный порядок не гарантируется.

Фоновые задачи используют отдельный пул из четырёх соединений, в дополнение к API-пулу. Это изолирует ожидание соединений, но не CPU/IO PostgreSQL и не нагрузку на брокер. HTTP transport сохраняет до 64 соединений на получателя. Фактическая скорость зависит от задержек HTTP, БД и числа экземпляров; конфигурацию нужно проверять на целевом окружении.

`WMS_MONITOR_ADDR` по умолчанию `127.0.0.1:9091`; разрешён только буквальный loopback IP. `/metrics` публикует Prometheus counters/gauges, `/health/background` — JSON-снимок и 200/503. Это общие показатели установки; порт предназначен для локального агента мониторинга, не для публичного ingress. Локальные процессы считаются доверенными.

Наблюдение обновляется раз в 5 секунд. Метрики: доставки/ошибки/ошибки claim, освобождённые резервы/ошибки expiry, pending/dead, возраст старейшего pending и просроченного резерва, timestamp каждого цикла. Успешный claim обновляет relay heartbeat даже при временном отказе получателя; ошибочная доставка не считается успешной. Ошибки мониторинга не затирают последний успешный timestamp.

`/health/background` возвращает 503 до первых успешных проходов, при heartbeat старше 20 секунд, наличии dead events или возрасте очереди/просроченного резерва свыше 60 секунд. `/readyz` зависит от БД, а `/livez` проверяет живой процесс. Отказ брокера, dead events и очередь не снимают здоровый складской API с балансировки. Операции остаются атомарными в PostgreSQL, события ожидают доставки в durable outbox.

Оповещения следует настроить на `wms_background_ready == 0`, dead > 0 и превышение возраста очереди; сравнивать скорость прироста `wms_outbox_delivered_total` с входным потоком. Готовые Prometheus/Alertmanager и правила окружения не разворачиваются этим изменением. В метриках нет payload, credentials и идентификаторов организаций.

## Обновление установки

1. Сделать резервную копию и остановить старые backend-процессы. Сначала проверить путь на восстановленной копии базы.
2. Применить core до 0009 через `scripts/migrate_core.py`; для подтверждённой старой установки без core-журнала использовать явный `--legacy-through 0007` или `0008`. Online-рецепт 0008 сохраняет OID guard-функции и создаёт индекс concurrently. Исходные выпущенные миграции неизменны. Подробности: [warehouse-workflow.md](warehouse-workflow.md).
3. Повторно применить `backend-grants.psql` для новых контрактов и функций.
4. Если установлен dispatch-quality 1.0, сначала выполнить переход 1.0 → 1.1. Для 1.1 один раз применить `003_authoritative_guard.sql`, затем `db/examples/upgrade_dispatch_quality_1_2.psql`. Скрипт сверяет историю, сохраняет решения и повторяем для точной 1.2.0. Создать действующую policy и выдать quality.approve проверяющим.
5. Для остальных compiled-пакетов установить SQL-guards и привязки. Подготовить брокер, ключ, TLS и наблюдение.
6. Запустить binary 0.5.0. Несовместимая установка завершает startup с ошибкой.

Менеджера установки, автоматического rollback схемы и гарантий HA ещё нет. При rollback binary нельзя удалять requirements или возвращать функции проведения к версии до 0006. Нужен совместимый binary либо исправляющая forward migration.

## Проверки

`docs/verification/security-red.json` сохраняет исходные падения до реализации. `security-green.json` — результат полного локального прогона. CI `.github/workflows/security.yml` поднимает PostgreSQL, использует тот же `prepare-test-db.py`, выполняет форматирование, vet, проверку зависимостей, go fix изменённых пакетов, race/integration, SQL kernel и govulncheck. Summarizer требует критические security-тесты и отклоняет skipped/fail. Actions закреплены по SHA, permissions — contents:read, checkout credentials не сохраняются.

Workflow сам не делает проверку обязательной для merge: branch protection/ruleset настраивает владелец репозитория отдельно. Настройки доступа GitHub здесь не менялись. Локальные тесты не заменяют проверку реального брокера, аварийного восстановления, HA и независимый аудит безопасности.

Проверки изменения 0.5.0: `background-red.json` фиксирует исходные воспроизведения, `background-green.json` — актуальный прогон. Burst-тест с реальными PostgreSQL и TLS HTTP измеряет локальную пропускную способность; он не доказывает SLO произвольного клиентского брокера и не является длительным soak-тестом.

Регрессии 0.6.0: `verification/warehouse-green.json`, `verification/migrations-green.json`, `verification/readiness-outage.json`. Последний отчёт фиксирует реальные отключения TLS-приёмника на 120 и 300 секунд и восстановление без изменения часов/таймеров SQL. Это локальная проверка TCP/TLS и durable outbox; конкретный брокер заказчика проверяется отдельно.
