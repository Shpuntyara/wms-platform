# Hardened-v1 deployment profile

The legacy runtime contract trusts a caller-supplied actor UUID and grants warehouse-global contract reads plus maintenance functions. An SQL password holder can use that contract without OIDC. The binary now defaults to `hardened-v1` and fails startup without its configuration. Explicit `WMS_DATABASE_PROFILE=legacy` retains the old trusted-role behavior and emits a warning. Existing deployments must install the additive profile and provision its roles/key before upgrading, or explicitly accept the legacy risk.

`db/profiles/hardened-v1.sql` adds a separate SQL surface after core 0009; it does not replace a published migration or checksum. `postgres.NewHardened` implements `api.Backend`; `postgres.NewHardenedWorker` implements the maintenance worker. The command entry point selects both adapters when `WMS_DATABASE_PROFILE=hardened-v1`, rejects missing or unknown configuration, and verifies separate effective logins with matching organization and warehouse bindings.

## Threat model and boundaries

The attacker possesses only one SQL service login. They have no OIDC bearer token, application request-context key, installation owner/admin access, or ability to execute code in the application process. The SQL service role cannot issue itself an authenticated user identity. An independently held 32-byte application key provides that missing boundary; an ordinary `SET wms.actor_id` or unsigned GUC is never accepted as identity.

Each API login is administratively bound to exactly one organization and warehouse. A separate worker login is bound to that same deployment scope. API logins cannot call maintenance functions; worker logins cannot resolve users, read API resources, or post API commands. Shared roles and role memberships are rejected. No unscoped business view, table, or module facts grant is required.

The API signs a short-lived context only after its existing OIDC verifier has supplied an identity. The payload is the UTF-8 bytes of nine pipe-separated fields: protocol `1`, session login, backend PID, 64-bit transaction ID, actor UUID, organization UUID, warehouse UUID, Unix expiry seconds, and lowercase SHA-256 of the exact action bytes. The application uses a 20-second expiry; SQL rejects expired contexts or lifetimes above 30 seconds. Action bytes are `resolve|` plus the exact JSON identity array, `read|RESOURCE|` plus the exact raw JSON input, or `command|UUID|KIND|` plus the exact raw JSON input. The boundary RPC accepts `text` and verifies the MAC before parsing JSON. No canonical JSON or client-set actor parameter is trusted. Context transport uses transaction-local GUCs; every RPC verifies its signature again.

HMAC-SHA256 uses PostgreSQL's `pgcrypto` implementation and Go's standard library. The private verifier compares all 32 signature bytes with fixed work. Contexts cannot move to another backend or transaction, change action/arguments, or select another administrative scope. Repeating precisely the same command in its original transaction remains valid; core command IDs provide durable idempotency across fresh, newly signed transactions. [PostgreSQL HMAC](https://www.postgresql.org/docs/17/pgcrypto.html), [session and transaction identifiers](https://www.postgresql.org/docs/17/functions-info.html).

Business permissions and owner limits are read from current `platform.actor_grants` in SQL immediately before reads or commands. Core accounting, document locking, quality guards, and idempotency still run in the existing kernel. The wrapper uses protected `SECURITY DEFINER` functions with `search_path=pg_catalog` and explicitly qualified objects; runtime receives execution rights only on the named RPCs. [Security-definer precautions](https://www.postgresql.org/docs/17/sql-createfunction.html).

Remaining consequences are material:

- A stolen API login can connect, consume DB resources, inspect ordinary PostgreSQL metadata and the allowed module manifest/migration metadata, and disrupt sessions sharing its role. This profile does not solve denial of service or hide catalog object names.
- A stolen worker login can read event payloads and acknowledge/discard leased events inside its own warehouse; it can expire genuinely expired reservations there. The worker is necessarily trusted for those actions. Warehouse separation contains its reach, not its own queue integrity.
- Application key theft, OIDC compromise, application RCE, an SQL injection inside an already signed legitimate request, and owner/admin compromise are outside the password-only claim. Exact-action binding limits reuse but cannot make a compromised application trustworthy.
- A valid signed request may remain usable for its exact action in its original transaction until expiry. There is no per-request nonce ledger; transaction binding and durable command IDs serve distinct purposes.
- Backend startup rejects missing profile/key, key mismatch, unsafe role attributes, group membership, database CREATE rights, and legacy schema grants. Administrative privilege drift after startup requires restart/preflight; the attacker cannot create that drift using the permitted service login.
- One process serves one warehouse binding. Multiple warehouses require separate bound deployments/logins; granting a shared global role defeats the design.
- The profile does not claim HA, broker delivery integrity against the worker itself, performance equivalence for large reads, independent audit completion, or protection of unrelated databases.

## Installation and startup

1. Apply the unchanged core migrations through 0009. Install the optional SQL profile as the core installation owner, with authority to create the `pgcrypto` extension in its dedicated `hardened_crypto` schema. This initial profile expects a fresh extension installation; an existing differently located extension must be reviewed by the installation administrator. Install module schema/guards as usual under installation ownership.
2. Have the database administrator provision two distinct LOGIN roles with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, no object ownership and no role memberships. Use separate credentials and the deployment's existing TLS/authentication management.
3. Apply `db/bootstrap/hardened-grants.psql` as the installation owner, passing psql variables `api_role`, `worker_role`, `organization_id`, and `warehouse_id`. It strips direct legacy grants before granting only the profile functions. Bootstrap and binding changes are owner operations; runtime cannot edit either private table. Existing PUBLIC/group grants are not silently repaired: startup rejects a resulting unsafe scope.
4. Provision one random 32-byte request key independently of SQL passwords and `WMS_OUTBOX_HMAC_KEY`. Administrator tooling writes `(api login, raw bytea key)` to `hardened_private.signing_keys` through a parameterized owner connection. The application receives the same bytes encoded as base64 through its secret configuration. Do not place the key in migration text, psql arguments, a source file, or a verification receipt. Key rotation replaces both the owner-held key and application configuration; mismatched instances fail closed.
5. In the integrating binary, explicitly select `WMS_DATABASE_PROFILE=hardened-v1`, set `WMS_DATABASE_URL` to the bound API login, `WMS_WORKER_DATABASE_URL` to the distinct worker login, and `WMS_REQUEST_CONTEXT_KEY` to the separate request key. Both pools retain the existing database TLS requirements. Unknown profile values and missing hardened configuration must reject startup. Legacy `postgres.New` cannot initialize with the restricted login.
6. Module startup reads a protected metadata RPC and checks projection columns with `LIMIT 0` under the installation owner. Do not run legacy module runtime-grant scripts against hardened logins: granting `USAGE` on `mod_*` makes hardened startup reject the role. The kernel owner still needs access to required module guards/projections.

Binding/bootstrap is intentionally one-time and fails on duplicate bindings rather than silently repurposing an existing login. Installation management must review any scope changes. Logins that still belong to an old runtime group need fresh dedicated roles.

Both DSNs must target the same configured host, port and database. Fallbacks may vary TLS mode on that endpoint; multi-host/port fallbacks are rejected to prevent the two pools silently selecting different database endpoints. This check does not prove a load balancer's topology or HA behavior.

## Reproducible verification

Run `scripts/test-hardened-profile.ps1 -PgBin <PostgreSQL bin> -GoExe <go executable> -IncludeMutations`. It creates a disposable loopback-only cluster inside this checkout's `work/`, preserves receipts in `docs/verification/security-arena/`, and stops its cluster. It never uses a production DSN, writes a password, or persists the synthetic application key outside the disposable database.

The original RED receipt preserves five actual baseline violations: foreign-document enumeration, actor forgery through reserve, outbox claim, outbox acknowledgement, and expiry execution. A separate actual RED found same-transaction read-signature reuse for commands; action binding fixes that case. Current SQL tests cover forged/missing/expired/tampered contexts, exact raw bytes, cross-backend/transaction replay, scope limits, and legitimate reads/commands with rollback. Real Go HTTP tests use the full backend with race detection, current-grant revocation, separate workers, concurrent idempotency, and before-send/after-ack COMMIT failures followed by safe retry. Module tests prove startup succeeds without exposing fact rows and rejects a missing required projection.

Four executable mutations disable MAC checking, action binding, worker claim scope, or document candidate bounds in SQL installed only into a disposable database. Their tests must fail on the corresponding behavior; build failures, timeouts, skipped tests and stale receipts do not count as kills. Each run writes query plans into its own directory. `white.json` records the initial candidate's local evidence and limits. Full integrated CI and independent attack results are separate release evidence and must not be inferred from these local passes.

Document reads also run against 100,000 documents and 300,000 lines with 30 deterministic randomized owner-grant/page-size cases and an independent in-memory pagination oracle. With `WMS_HARDENED_PLAN_DIR` set, the test saves the actual internally generated SELECT and 14 executed custom/generic plans. A real RED exposed approximately 99,000 scanned rows for a 21-document page. The forward profile now resolves current grants into bounded owner candidates and applies cursor bounds before hydration, using the existing core UNIQUE FK indexes; no new indexes are created. The local GREEN plans processed 210–585 row-work units and hydrated at most 21 documents. These are structural laboratory bounds, not production latency or throughput guarantees. A separate 180-second fixture-construction timeout was diagnosed as CPU-bound with no blocking session, retained as failed setup evidence, and excluded from all pass/mutation claims; parent-table statistics are refreshed before the large FK-backed line insert.
