# WMS: нагрузка и устранение узких мест — 27 октября 2026

Проверены параллельные резервы/движения, горячие балансы и чтение большой истории. Исправлены запросы курсорных страниц и добавлены три индекса. Учётные команды, обязательные guards и порядок блокировок сохранены. Текущий patch ядра — **0.3.1**, SDK остаётся **2.0.0**.

## Стенд и данные

Windows/amd64, Ryzen 5 5600X (6 ядер/12 потоков), 32 ГБ RAM, Go 1.27.3, PostgreSQL 17.11. Пул API — 20 соединений, shared_buffers — 256 MiB. `fsync`, `synchronous_commit`, `full_page_writes` включены. Приложение, клиент и БД находятся на одной машине.

Исходный набор: **1 000 000 движений**, **250 000 освобождённых резервов**, **100 000 балансов**, два склада, 100 владельцев, один SKU. Есть соответствующие операции, строки движений, события резервов, аудит и доставленный outbox. Полный набор занимает около 4,2 GiB. История сформирована пакетным SQL; нагрузочные команды исполнялись через HTTP API с настоящей проверкой RSA JWT, runtime-ролью и обязательным синтетическим guard.

Фазы стартовали с отдельных копий одного seed database. Измерения последовательные; race detector в замерах скорости выключен. Для HTTP-бенчмарков — 10 повторов по 20 измеряемых запросов после прогрева; для записи — по три 3-секундных окна на каждое сочетание сценария и числа клиентов с завершением начатых циклов. Подготовка и сверка не входят в эти окна.

## Подтверждённая проблема и исправление

API сортирует страницы по UUID. Прежние индексы имели промежуточные поля перед `id`, а условия `optional owner OR ...` и `nullable cursor OR id > ...` мешали generic prepared plan использовать точные границы. Даже первая страница одного владельца могла сортировать весь подходящий участок истории.

Теперь List формирует отдельные параметризованные формы для одного/нескольких/всех владельцев и наличия курсора; для выбранного владельца по-прежнему выполняется проверка допуска. Курсор передаётся прямым `id > $N`. Миграция `0005` добавляет `(organization_id,warehouse_id,owner_id,id)` для движений, резервов и остатков через `CREATE INDEX CONCURRENTLY`.

Отдельный тест по логической работе сначала падал на прежней реализации, затем прошёл: страница до 51 читаемой строки укладывается в 1000 обращений к shared buffers и с custom, и с generic plan. Это обращения, включая повторные cache hits, а не объём физического чтения с диска. В диагностическом снимке глубокая страница движений сократилась с примерно 926 тысяч обращений до **260**. В автоматическом режиме исходный сервер обычно выбирал более быстрый custom plan, поэтому этот диагностический разрыв не равен ускорению обычного HTTP-запроса.

## Конкурентная запись и предел горячей строки

| Сценарий, 64 клиента | До, HTTP-команд/с | После, HTTP-команд/с | После, медиана p95 трёх прогонов |
|---|---:|---:|---:|
| Резерв + отгрузка одного баланса | 508 | 498 | 216 мс |
| Резервы + переносы + отгрузки общей пары | 549 | 548 | 190 мс |
| Тот же SKU в независимых балансах | 1677 | 1659 | 57 мс |

Это описательные медианы трёх коротких прогонов; статистическое улучшение или точная эквивалентность записи не заявляются. Разброс перекрывается, существенного ухудшения на стенде не наблюдалось. HTTP-команды/с не являются количеством заказов/с: один цикл содержит две или три команды.

Основной предел записи здесь — сериализация **одного баланса**, затем ожидание пула. При разделении того же SKU по независимым балансам пропускная способность заметно выше. Снимать учётные блокировки или проверять доступность по кэшу для такого ускорения нельзя. Кумулятивное ожидание пула в JSON суммируется по клиентам и может превышать длительность окна.

Дополнительно один прогон чтения с 16 клиентами дал для глубокой страницы движений владельца около **582 → 2010 HTTP-запросов/с**, p95 **46 → 14 мс**. Это отдельный короткий профиль, не статистическая оценка максимальной мощности системы.

## Корректность и цена изменений

- Во всех измеряемых фазах — **0 технических ошибок** и успешная сверка учёта с журналом, резервами, аудитом и outbox.
- 64 попытки забрать 10 единиц: **10 успешных резервов, 54 ожидаемых `409`**.
- 64 одинаковых command IDs: **один резерв и один запуск guard**, 64 ответа с сохранённым результатом.
- 64 разных команды с одной версией документа: **одна успешная, 63 ожидаемых конфликта версии**.
- Проверены пустая, одиночная, множественная и wildcard-области владельцев, разрешённый/запрещённый фильтр и проход по курсорам.
- Все три новых индекса валидны; после профиля занимают примерно **86,1 + 24,4 + 8,3 = 118,8 MiB**. Это дополнительное место и стоимость поддержки при записи, их нужно учитывать в поставке.
- Отдельный запуск нагрузочного harness с `-race` прошёл на меньшем наборе. Полный обычный regression: 217 событий успешных тестов с учётом подтестов, 41 SQL-сценарий, ошибок и пропущенных тестов нет.
