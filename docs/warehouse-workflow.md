# Складские документы 0.6.0

Реализован первый сквозной сценарий backend на заранее настроенном складе, с существующими товарами, владельцем товара и адресами/остатками. Оператор создаёт документы через API, активирует их и проводит фактические операции. Справочники пока настраиваются администратором; UI терминала, задания сотрудникам, сканирование штрихкодов, подбор адресов/FEFO и частичное закрытие с расхождениями — следующие продуктовые части.

## Контракт документов

`GET /api/v1/documents` — список с курсором и фильтром `owner_id`. `GET /api/v1/documents/{id}` возвращает строки с `requested_qty`, `reserved_qty`, `fulfilled_qty`. Для обоих нужны `organization_id`/`warehouse_id` в query и право `document.read` на соответствующего владельца. Фильтры item/position/document_line для документов не поддерживаются и возвращают 400.

`POST /api/v1/documents` требует `document.create`, Bearer token и `Idempotency-Key` UUID. Пример тела:

```json
{
  "organization_id": "<organization-uuid>",
  "warehouse_id": "<warehouse-uuid>",
  "owner_id": "<stock-owner-uuid>",
  "kind": "receipt",
  "number": "IN-2026-0001",
  "lines": [{"item_id": "<item-uuid>", "quantity": "4"}]
}
```

Виды: `receipt`, `transfer`, `shipment`, `adjustment`. Документ создаётся в `draft`, версия 1; все строки создаются в той же транзакции, от 1 до 200 строк. Номер обязателен, до 100 Unicode-символов, уникален в рамках склада и вида документа. Количества положительны, передаются строкой и проверяются по точности SKU. Создание возвращает `201`, `data.document_id`, `document_version`, `content_revision`, `state`, `lines[].id`. Плановые строки в этом выпуске неизменяемы: ошибочный черновик можно отменить и создать новый.

`POST /api/v1/documents/{id}/transitions` требует отдельного права `document.transition` и нового `Idempotency-Key` для каждой новой команды:

```json
{
  "organization_id": "<organization-uuid>",
  "warehouse_id": "<warehouse-uuid>",
  "expected_document_version": 1,
  "state": "active"
}
```

Разрешены draft → active/cancelled и active → closed/cancelled. Активация увеличивает версию и content_revision. Закрытие требует полного исполнения каждой строки и нулевых резервов. Отмена требует отсутствия исполненного и зарезервированного количества. Закрытые и отменённые документы не открываются повторно. Неверная версия, недовыполнение и запрещённый переход дают 409. Чужой документ недоступен через API; права проверяются также в SQL entrypoint.

Создание и переход атомарно создают запись операции, аудит и outbox. Точный повтор возвращает первоначальный результат; повтор ключа с другим телом даёт 409. При потере ответа нужно повторять тот же запрос с тем же ключом. Бизнес-решения по остаткам/резервам и guards модулей выполняет существующий SQL kernel. Активация и закрытие не проводят товар; revision изменяется, поэтому старое одобрение клиентского модуля не становится разрешением для нового содержимого.

## Проверяемый сценарий

1. Создать receipt на 4 единицы и активировать (версия 2). Провести receipt на адрес приёмки, затем закрыть документ с версией 3.
2. Создать transfer на 4 единицы и активировать. Провести transfer на адрес хранения и закрыть документ.
3. Создать shipment на 4 единицы, активировать, зарезервировать количество на адресе хранения. Закрытие и отмена с этим резервом отклоняются.
4. Провести transfer с reservation_id на адрес отбора/отгрузки. Kernel возвращает new_reservation_id: именно он используется для последующего issue.
5. Провести issue по перенесённому резерву. После полного исполнения закрыть shipment. Остатки сверяются с журналом, активного резерва больше нет.

Исполняемый HTTP-сценарий: `internal/postgres/store_documents_integration_test.go`, тест `TestWarehouseReceiptPutawayPickAndShipViaAPI`. В тесте используются настроенные адреса; назначение и выбор физических зон — ответственность настройки склада. Специальные правила зон могут быть введены клиентским SQL guard. Новые документы проходят те же проверки движений и отгрузки, что и существующие.

## Readiness и отказ брокера

`/readyz` возвращает 200 при доступной БД API и 503 при её недоступности. Фоновая очередь, ошибки доставки и dead events публикуются на loopback `/health/background` и `/metrics`. Их нельзя использовать как readiness складского API. Во время отказа брокера записи продолжают атомарно создавать outbox; внешний получатель должен дедуплицировать event_id. Backoff и лимит попыток остались прежними; после исчерпания попыток dead events требуют решения оператора.

Выполнены реальные отказы TLS-приёмника на 120 и 300 секунд. В длинном прогоне созданы 1500 резервов через API и затем доставлены все 1501 событие этой организации без dead events. Восстановление заняло 256.194 секунды после возврата приёмника из-за обычного backoff; длительность сценария превысила 9 минут. Проверялись readiness и чтение остатков, а не только запись очереди. Отчёт: `verification/readiness-outage.json`. Для повтора локально:

```powershell
./scripts/test-postgres.ps1 -PgBin 'C:/Program Files/PostgreSQL/17/bin' -GoExe '<go.exe>' -PythonExe '<python.exe>' -BrokerOutageSeconds 300 -Report work/outage.json
```

## Безопасное применение core

Нужны Python 3 и psql; это release-команда, backend не мигрирует базу при запуске. Запускать владельцем схемы. Параметры libpq передавать через PGSERVICE/PGPASSFILE, не хранить пароль в команде/репозитории.

```text
python scripts/migrate_core.py --database <database> [--owner-role <schema-owner>]
```

Одна сессия сериализует миграторы advisory lock. Журнал `wms_migrations.history` хранит хэш исходного SQL и исполняемого рецепта. Точный повтор пропускает завершённые шаги, расхождение хэшей останавливает обновление. Receipt транзакционной миграции фиксируется вместе с DDL. `0005` и индекс `0008` выполняются concurrently вне транзакции; проверяются готовность, валидность, таблица, набор столбцов и предикат индексов. Неверный/INVALID индекс требует явного исправления; мигратор не удаляет его автоматически. Завершённые индексы после прерывания можно использовать при повторе.

Исходные `0001`–`0008` не изменены. Для `0008` используется отдельный проверяемый рецепт, привязанный к хэшу исходника: v1-функция копируется под новым именем, исходная функция заменяется через CREATE OR REPLACE с сохранением OID, grants и зависимостей. Блокирующий CREATE INDEX внутри старого файла не выполняется. Не запускать `0008` вручную по старой инструкции. Lock timeout — 2 секунды; statement timeout — 10 минут для concurrent index и 30 секунд для нового DDL документов. Ошибка шага не означает успешное обновление; повторять после устранения причины. Возврат версии приложения не удаляет миграции и историю.

Для старой установки без core-журнала обычный запуск специально отказывает. Если журнал релизов подтверждает, что на базе полностью применён выпуск до `0007` или `0008`, после резервной копии и проверки на её восстановленной копии выполнить один раз:

```text
python scripts/migrate_core.py --database <database> --legacy-through 0007
```

Либо `0008` для уже обновлённой установки. Параметр — явное утверждение оператора о прошлом релизе. Catalog probes отсеивают несовместимую форму схемы, но не доказывают отсутствие ручных изменений; записи принятых старых шагов помечаются `legacy_baseline`, а не выдуманными исполнениями. После перехода запускать без этого параметра. Более старые/изменённые вручную базы сначала требуют сверки схемы; автоматического baseline нет.

После core повторно применить `db/bootstrap/backend-grants.psql` с нужным runtime_role. Выдать `document.read`, `document.create`, `document.transition` нужным actor_grants с областью организации/склада/владельца. Процедура обновления dispatch-quality остаётся отдельной. Backend 0.6.0 при старте проверяет новый read contract, поэтому новую версию запускать после migration + grants; старый binary продолжает использовать прежние additive contracts. Проверены переходы с `0007` и `0008`; online-переход с `0007` сохраняет OID и зависимый view. Прогон `scripts/verify-migrations.py` встроен в CI.
