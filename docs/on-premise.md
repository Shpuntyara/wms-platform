# On-premise WMS

Один клиент получает независимую установку WMS, отдельную PostgreSQL БД и сервер. Общей клиентской БД, tenant registry и SaaS-маршрутизации нет. Организации, склады и владельцы товара — внутренние области прав этого клиента. Один API и один worker обслуживают несколько складов; отдельные процессы и SQL logins для каждого склада не требуются.

## Границы доступа

- API и worker используют разные непривилегированные SQL logins одной установки. Startup сверяет UUID установки, фактические logins и адрес БД. UUID идентифицирует установку и сохраняется при её аварийном восстановлении.
- OIDC принадлежит инфраструктуре клиента; HTTPS issuer/JWKS можно разместить в его локальной сети. Права берутся из текущих DB grants, а не из произвольных JWT roles или тела HTTP-запроса.
- API подписывает контекст конкретной операции независимым ключом: installation UUID, login, backend PID, transaction ID, actor, organization, warehouse, expiry и точные аргументы. SQL повторно проверяет подпись и текущие права пользователя. Один пользователь может иметь права на несколько складов.
- Worker выполняет обслуживание всей клиентской БД через существующие kernel-функции. Его login доверен для claim/ack событий и освобождения истёкших резервов всей этой установки; это не пользовательская учётная запись. API login не получает эти возможности.
- Владелец схемы, provisioning и локальный администратор остаются привилегированными. Этот профиль не защищает от администратора, который может переписать БД, или от захвата процесса приложения вместе с ключами.

## Установка и переход

Новые установки используют `WMS_DATABASE_PROFILE=onprem-v1`; пустое значение выбирает тот же профиль. Старый `hardened-v1` больше не выбирается бинарником: он сохраняется как неизменённый исторический SQL-этап. Явный `legacy` сохраняет прежний доверенный SQL-контракт и его риск.

Переход выполняется в окне обслуживания, после свежего backup и проверки restore на изолированной копии:

1. Остановить приём новых команд и корректно завершить текущие запросы/worker. Сохранить идентификаторы неподтверждённых команд для повтора с теми же ID.
2. Применить неизменённые core migrations через существующий migration runner. На новой БД установить `db/profiles/hardened-v1.sql`; существующую установку этого профиля повторно не создавать.
3. Применить **новый** `db/profiles/onprem-v1.sql` как installation owner. Он атомарно создаёт идентификатор установки, сохраняет существующие signing keys и logins и снимает ограничение service login одним складом. Бизнес-права сотрудников не расширяются. Таймаут ожидания DDL-блокировки ограничен.
4. Применить `db/bootstrap/onprem-grants.psql` с `api_role` и `worker_role`. Свежие logins должны быть различны, без административных атрибутов, владения объектами и group memberships. При повторе bootstrap проверяет соответствие типа роли.
5. Передать `WMS_DATABASE_URL`, `WMS_WORKER_DATABASE_URL` и независимый base64 32-byte `WMS_REQUEST_CONTEXT_KEY` через клиентский менеджер секретов. Ключ соответствует приватной записи API login в БД; на первой установке его создаёт администратор. Не записывать его в исходники, SQL-миграцию, argv или журналы.
6. При переходе на новые logins закрыть прежние service logins, завершить их оставшиеся сеансы и отозвать прежние runtime grants. Создание новых защищённых logins само по себе не отзывает украденный старый пароль.
7. Запустить новый бинарник, проверить readiness, права пользователей разных складов и safe retry неподтверждённых команд. Readiness проверяет актуальный UUID, ключ и настройки сохранности БД; изменение этих параметров не должно оставлять ложный `200`.

Обратный запуск старого бинарника после нового SQL-профиля не является откатом. До возобновления записи возможен только заранее проверенный возврат всей установки. Если после обновления уже подтверждены команды, восстановление старого backup без учёта этих команд потеряет данные; в таком случае нужен согласованный forward fix или процедура восстановления с доказанным endpoint.

## Сохранность и точность

Для запуска обязательны `fsync=on`, `full_page_writes=on`, `data_checksums=on`, а также `synchronous_commit=on` или `remote_apply`. Режимы обхода повреждения страниц `ignore_checksum_failure`, `zero_damaged_pages`, `ignore_invalid_pages` должны быть выключены. Новая установка включает checksums при `initdb`; их включение на существующем кластере — отдельная offline-операция администратора, не автоматическое действие приложения.

Перед бизнес-SQL транзакция усиливает ослабленный session `synchronous_commit` до `on`, сохраняя `remote_apply`, и снова проверяет настройки сохранности. При небезопасной конфигурации запись отклоняется. Worker применяет ту же политику и не возвращает события как успешно полученные при неподтверждённом COMMIT.

Количество хранится как точное десятичное `numeric`, без float в учётном ядре. PostgreSQL выполняет проверки точности товара, диапазона, неотрицательности, резервов, версий документов и неизменности истории. Тесты микродолей сверяют реальные параллельные команды с независимой целочисленной моделью; ошибки должны откатывать операцию целиком. Неопределённый результат COMMIT требует повтора исходной команды с исходным ID.

Включённые checksums обнаруживают повреждение страниц; они не заменяют восстановление. При checksum error нельзя включать обход проверки или автоматически занулять страницы: остановить запись, сохранить диагностику и использовать проверенный backup/WAL-план.

## Эксплуатация одного сервера

Один физический сервер остаётся единой точкой отказа. Рекомендуемая аппаратная основа — UPS, надёжное хранилище с корректным flush и, где доступно, ECC/зеркалирование. RAID не заменяет backup. Добавление HA потребует отдельной топологии, fencing и проверки failover; оно не появляется от настройки приложения.

Обязательны зашифрованные версионные копии за пределами этого сервера и регулярные restore rehearsal. Backup должен включать все схемы клиента, installation identity/signing metadata, роли/grants и отдельно управляемые секреты приложения. Файл логического dump в CI содержит только синтетические данные и не является готовой системой production backup.

Для PITR нужны физический base backup и непрерывная проверенная цепочка WAL. Периодический `pg_dump` не доказывает PITR или нулевой RPO. Не задавать SLA по лабораторному времени восстановления.

Restore сначала выполняется в изоляции: без производственного брокера, потребителей и реальных учётных данных. Сверяются контрольные суммы backup, полный журнал подтверждений, идентификаторы команд, остатки, резервы, ledger/audit/outbox, grants и metadata. Только после этого допустимо планировать переключение. Сборщик evidence отказывается публиковать `passed` при отсутствующем dump или усечённом witness.

## Проверяемые сценарии

CI выполняет core/race/SQL regressions, property based учёт с микродолями на нескольких складах, многоскладской on-premise API, текущие права владельцев, смену ключа/UUID, реальные небезопасные PostgreSQL конфигурации, мутации и SIGKILL → WAL recovery → isolated restore. Крупное чтение сохраняет custom/generic EXPLAIN планы на 100000 документов и 300000 строк.

Это доказательства конкретных программных и синтетических восстановительных сценариев. Они не доказывают отсутствие любых ошибок, честность дискового cache клиента, устойчивость при потере питания, физической гибели сервера или production RPO/RTO. Полный CI проверяется на итоговой ревизии без пропусков обязательных шагов.

Справочные основания: [PostgreSQL WAL settings](https://www.postgresql.org/docs/17/runtime-config-wal.html), [data checksums](https://www.postgresql.org/docs/17/checksums.html), [backup and restore](https://www.postgresql.org/docs/17/backup.html).
