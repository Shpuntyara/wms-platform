# Go backend WMS

Ядро 0.4.0, SDK 2.0.0, Go 1.27.3, стандартный `net/http`, pgxpool и PostgreSQL kernel. API содержит чтение остатков, резервов, движений и результатов команд; создание/освобождение резервов и проведение движений. Полный контракт — `api/openapi.json`. [Аудит структуры](reviews/2026-10-27-backend-audit.md) и [нагрузочная проверка](load-testing.md).

Актуальный порядок установки, SQL-защита и relay описаны в [документе безопасности](security-hardening.md).

## Доступные API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/stock-balances` и `/{id}` | Остатки и доступное количество |
| `GET /api/v1/reservations` и `/{id}` | Резервы и их исполнение |
| `POST /api/v1/reservations` | Резервирование |
| `POST /api/v1/reservations/{id}/releases` | Освобождение резерва с причиной |
| `GET /api/v1/movements` и `/{id}` | Проведённые движения и строки |
| `POST /api/v1/movements` | Приёмка, перенос, отгрузка, корректировка |
| `GET /api/v1/operations/{id}` | Результат команды исходного автора |
| `GET /livez`, `GET /readyz` | Жизнеспособность процесса и доступность БД |

Чтение требует `organization_id` и `warehouse_id` в query. Разрешения ограничивают владельцев товара. Списки имеют непрозрачный курсор, связанный с автором, областью и фильтрами; `limit` от 1 до 200, по умолчанию 50. Порядок — по UUID, он стабилен, но не означает хронологию. Списки не являются снимком состояния на протяжении нескольких HTTP-запросов.

Изменяющий запрос требует UUID в `Idempotency-Key`, ожидаемую версию документа и количество десятичной строкой. Числовой JSON, отрицательные/нулевые количества, более 6 дробных разрядов, неизвестные поля, лишний JSON и тело более 1 MiB отклоняются. Причина ограничена 2000 Unicode-символами, включая кириллицу. Реальная допустимая точность товара дополнительно проверяется ядром БД.

Одинаковый повтор получает прежний ответ `201`; изменённые параметры с тем же ID дают `409`. После сетевого обрыва клиент повторяет исходный запрос с исходным ID. Новый ID означает новую бизнес-команду. `404` при проверке результата не доказывает, что параллельно исполнявшаяся команда не завершилась.

## Авторизация

Backend принимает JWT access token через `Authorization: Bearer ...`. Проверяются HTTPS issuer/JWKS, каждый переход редиректа, подпись RS256/ES256, audience ресурса, срок, subject, nbf и назначение access token. Поддерживаются `typ=Bearer` (например, Keycloak), `token_use=access` или JWT-заголовок `at+jwt`. ID tokens и непрозрачные токены не поддерживаются.

OIDC используется для проверки личности. Права из произвольных JWT roles/groups, HTTP-заголовков и тела запроса не принимаются. `(issuer, subject)` сопоставляется с `platform.actors`, затем читаются актуальные `platform.actor_grants`. Несуществующий пользователь без выданных прав получает отказ. Токены и Authorization не журналируются.

Разрешения: `stock.read`, `reservation.read`, `reservation.create`, `reservation.release`, `movement.read`, `movement.create`, `movement.adjust`, `operation.read`. Корректировки требуют отдельное `movement.adjust`, а не обычное право проведения. Grant с `owner_id=NULL` разрешает всех владельцев только в указанной организации и складе. Для операций записи контекст документа, источника, назначения и резерва проверяется до создания команды и получения учётных блокировок.

Это сервис проверки access token; браузерный login, управление пользователями, выдача токенов, группы и интерфейс администратора в него не входят. Нужен настроенный провайдер OIDC с отдельным audience `wms-api`. Выдачу DB grants выполняет администратор через управляемое provisioning, а не конечный пользователь.

## Подготовка и запуск

1. Подготовить отдельную базу и владельца схемы `NOLOGIN/NOSUPERUSER`. Создать отдельный runtime login, не входящий в роль владельца. Backend откажется стартовать при административных полномочиях, доступе к опасной роли через `SET ROLE`, CREATE в схемах ядра и mod_* или прямой записи в таблицы, колонки и опубликованные представления ядра.
2. Один раз применить миграции `0001`–`0007` владельцем схемы. Старые миграции не изменены. `0005_inventory_pagination.sql` создаёт индексы CONCURRENTLY и должна выполняться вне внешнего BEGIN/COMMIT; при неудаче проверить INVALID index перед повтором.
3. Применить `db/bootstrap/grants.psql` и `db/bootstrap/backend-grants.psql` с переменными `runtime_role` и `module_role`. Их значения — подготовленные установщиком роли, а не пароли.
4. Настроить `.env.example` через менеджер конфигурации/секретов. Приложение читает переменные окружения; `.env` автоматически не загружается.
5. Выполнить `go build -o work/wms-api ./cmd/wms-api` и запустить полученный файл.

`WMS_DATABASE_URL`, `WMS_OIDC_ISSUER` и `WMS_OIDC_AUDIENCE`, `WMS_OUTBOX_URL` и `WMS_OUTBOX_HMAC_KEY` обязательны. По умолчанию HTTP слушает `127.0.0.1:8080`. Для production нужен HTTPS ingress перед backend. Для удалённого PostgreSQL запрещены plaintext и TLS без проверки сервера; локальный loopback/Unix socket допускает локальное подключение. При доступе с другого хоста нельзя использовать пример `sslmode=disable`.

`WMS_DB_MAX_CONNS` ограничивает пул (по умолчанию 20); бюджет соединений рассчитывается на все экземпляры приложения. На запрос установлен контекстный бюджет 5 секунд; блокировки БД ограничены 2 секундами, SQL — 5 секундами. Deadlock/serialization failure повторяется до трёх попыток с тем же ID и откатом целой транзакции. Бизнес-конфликт версии не повторяется автоматически.

HTTP имеет таймауты заголовков, чтения, записи и завершения. При остановке прекращается приём запросов, завершаются текущие запросы, затем закрывается пул. Сервис не применяет миграции при старте и не запускает PostgreSQL. Внешние TLS, rate limits, балансировщик, резервирование и резервные копии остаются частью поставки инфраструктуры.

Ошибки имеют `application/problem+json` по RFC 9457 со стабильным `code` и `trace_id`. Неожиданные ошибки и SQL-детали скрыты. `409` означает конфликт состояния/команды/guard, `503` — недоступность, таймаут или сбой обязательной проверки. Для неопределённого результата используется повтор исходного ID.

## Клиентские модули

Поддерживаются доверенные compiled-модули и ограниченные правила `declarative_v1` без отдельной Go-сборки. При запуске читаются активные манифесты из БД, проверяются версии кода/ядра/SDK, зависимости, конфликты, capabilities и все обязательные обработчики. Требования БД обязательны независимо от env; `WMS_REQUIRED_MODULES` может добавить требования. Registry повторно проверяется перед новой командой.

Обработчики и точки закрепляются кодом в `Module.GuardPoints`. Backend требует точного совпадения привязок с активным манифестом: нельзя убрать guard, перенести его на другую точку или добавить незаявленную привязку. Точки: `inventory.before_reservation.v1`, `inventory.before_release.v1`, `inventory.before_movement.v1`, `outbound.shipment_dispatch_guard.v1` (для issue). Все применимые guards должны разрешить действие. Panic, ошибка, превышение бюджета или неоднозначные факты вызывают отказ и rollback.

Скомпилированный пакет закрепляет `SchemaVersion` и `MigrationChecksums`. Startup проверяет каноническую схему, её версию в манифесте, точный набор ID/SHA256 в истории миграций и доступность projection. Недостающая, изменённая или неизвестная будущая миграция запрещает запуск. Сверка истории не доказывает отсутствие ручного изменения SQL-объектов администратором; миграции и DDL-доступ должны оставаться управляемыми.

Guard получает только контекст команды, неизменяемый снимок документа и JSON-факты своего модуля. Доступ к `pgx.Tx`, произвольный SQL и изменение остатков в SDK не передаются. Данные читаются из зарегистрированного `mod_<module_id>.document_facts_v1` в той же транзакции и для той же организации, склада, документа и content_revision. Допускается ноль или одна запись; две записи — недоступность проверки, а не выбор случайного разрешения.

Реестр неизменяем в течение жизни процесса. Установка, смена версии и конфигурации требуют согласованной поставки/перезапуска; горячей загрузки нет. Policies исполняются только в ограниченном runtime declarative_v1. Subscribers и external-worker runtime пока отклоняются; доставку потребителям организует внешний брокер. Frontend/UI и произвольные модульные HTTP-маршруты не входят в этот backend.

Код модулей доверенный и разделяет процесс. Контекстный таймаут не может принудительно остановить произвольный зависший код. Нужны соблюдение SDK, проверки и процессная изоляция для недоверенных компонентов. В guard нельзя выполнять сетевые операции или ждать человека.

## Пример dispatch quality

Пакет `modules/dispatch-quality` версии 1.2.0 содержит полный манифест и SQL-миграции; ему нужны ядро >=0.4.0 и SDK 2. Скомпилированная реализация находится в `internal/clientmodules/dispatchquality`.

Для новой установки: применить SQL пакета по порядку, затем `db/bootstrap/dispatch-quality-grants.psql` и `db/examples/enable_dispatch_quality.psql`. Примеры `db/examples/dispatch_quality_schema.sql`/`dispatch_quality_projection.psql` создают те же объекты для прежних проверок; одновременно оба пути применять нельзя. Backend работает с уже установленным пакетом; полноценный менеджер установки/обновления модулей пока не реализован.

Для существующей установки используйте [порядок обновления](security-hardening.md): он включает прежний переход 1.0 → 1.1 и новый переход 1.1 → 1.2.

Активация автоматически сохраняет обязательное требование в БД; env можно задать дополнительно. Сервис проверит наличие кода и доступность read projection. Модуль пропускает issue только при актуальном согласовании, непустом evidence reference и неистёкшем сроке. Изменение `content_revision` делает старое согласование неприменимым. Последнее решение определяет результат; прежнее разрешение не подставляется вместо нового отказа.

Образец проверяет метаданные решения. API ввода решения, загрузка фотографии, проверка существования байтов evidence и UI не реализованы: это следующая прикладная часть клиентского модуля. Запись решения блокирует документ trigger-функцией. SQL-guard также проверяет действующую policy и независимого reviewer с quality.approve.

## Транзакционная последовательность

`authorize → prepare → required guards → post → commit`.

Новая миграция добавляет prepare для резервирования и освобождения; движения используют существующий prepare. Повтор завершённой команды определяется раньше текущих guard/version, но после актуальной проверки доступа. Отказ guard, отмена HTTP-запроса и ошибка проведения откатывают запись операции и outbox. Commit с незавершённой подготовкой запрещён ограничением БД.

Обрыв при `COMMIT` имеет неопределённый результат: PostgreSQL мог сохранить данные. API возвращает `503` с указанием повторить исходный command ID; сам backend не повторяет неизвестный результат автоматически. Интеграционный тест обрывает получение серверного подтверждения после фиксации и проверяет, что повтор не создаёт второй резерв.

## Проверка

Тесты были сохранены отдельным коммитом `8c4a2d9` до появления реализации; первый red-прогон сохранён в `docs/verification/go-backend-red.json`. Дальнейшие обнаруженные случаи сначала воспроизводились тестами: пропущенный guard, противоречивые факты, отдельное право корректировки, конфликт изменённого ID и неподдерживаемые расширения.

Unit: `go test -race ./...`. Полный воспроизводимый прогон на Windows создаёт новый локальный кластер на свободном порту, применяет все миграции, запускает vet, Go integration/race и прежние SQL-сценарии, затем останавливает кластер:

```powershell
./scripts/test-postgres.ps1 -PgBin 'C:/Program Files/PostgreSQL/17/bin' -GoExe 'C:/path/to/go.exe' -PythonExe 'C:/path/to/python.exe'
```

Интеграционные тесты требуют `WMS_TEST_ADMIN_DSN` и `WMS_TEST_RUNTIME_DSN`, loopback и имя БД с префиксом `wms_kernel_test`. Если их запускать вручную без переменных, тесты будут пропущены. Скрипт итоговой проверки запрещает выдавать успех при пропущенных тестах.

OpenAPI проверяется Redocly CLI. Лицензионные lint-правила отключены, потому что коммерческая лицензия продукта ещё не выбрана; остальные recommended-правила применяются. Отчёт локальной проверки не означает измерения нагрузки, HA, отключения питания или развёртывания с настоящим IdP клиента.
