# Нагрузочные проверки WMS

Изолированный стенд проверяет настоящий HTTP API, RSA access tokens через тестовый HTTPS OIDC provider, runtime-роль PostgreSQL и обязательный синтетический guard. Внешние ingress/TLS, настоящий IdP и прикладные проверки конкретного клиента в эти замеры не входят.

## Данные и безопасность стенда

`scripts/test-load.ps1` создаёт отдельный кластер PostgreSQL на случайном loopback-порту в `work/load-<uuid>`. Существующие PostgreSQL-службы не меняются. DSN проверяется до подключения: только выделенная локальная БД с префиксом `wms_kernel_test`, включая все запасные адреса и совпадение admin/runtime.

По умолчанию создаются 1 000 000 движений, 250 000 полностью освобождённых резервов, 100 000 балансов, 100 владельцев и два склада. История содержит операции, строки движений, события резервов, аудит и доставленные outbox-события. Заполнение выполняется пакетным SQL администратором; команды нагрузочных клиентов проходят через API. Нормальные FK/checks/triggers и долговечность остаются включёнными. `fsync`, `synchronous_commit` и прочие параметры записываются в отчёт.

Перед измерениями выполняются ANALYZE/VACUUM и полная сверка учёта. Каждая фаза получает собственную копию одной исходной БД через PostgreSQL template. Новые команды не загрязняют исходный набор или другую фазу. Утилита не удаляет историю и не отключает её защиту.

## Сценарии

| Сценарий | Проверяемое поведение |
|---|---|
| `hot_balance` | Независимые документы резервируют и отгружают один общий запас |
| `mixed_hot` | Одновременные резервы, перенос части резервов и отгрузки через общую пару балансов |
| `sku_distributed` | Один SKU размещён в разных балансах; отличаем конкуренцию SKU от блокировки одной строки |
| `last_units` | 64 клиента конкурируют за 10 единиц; ровно 10 резервов, остальные получают ожидаемый `409` |
| `same_command` | 64 одинаковых запроса возвращают результат одной команды; guard выполняется один раз |
| `same_document` | 64 команды с одной версией документа: одна успешна, 63 получают конфликт версии |
| History HTTP | Первые/глубокие страницы движений, резервов и остатков; ограниченный владелец и все владельцы склада |

Для записи используются 1, 16 и 64 клиента; один документ принадлежит одному циклу клиента. Версии обновляются после каждого подтверждённого шага. Применимые guards остаются внутри транзакции. При завершении окна нагрузки начатые циклы завершаются; их задержки и время завершения входят в результат.

Драйвер имеет замкнутый цикл: следующий запрос клиента начинается после ответа на предыдущий. Это замер при фиксированном числе клиентов, а не доказательство работы при произвольной открытой интенсивности поступления. Нагрузочный генератор и сервер делят машину с PostgreSQL.

## Метрики и проверка результата

- Показаны p50/p95/p99, количество успешных ответов, ожидаемых `409` и технических ошибок, фактические HTTP-запросы в секунду.
- Снимаются ожидания пула, образцы `pg_stat_activity`, SQL из `pg_stat_statements` и размеры таблиц/индексов. Вложенные SQL-измерения пересекаются: их время нельзя суммировать как длительность одного запроса.
- HTTP-бенчмарки повторяются 10 раз; `benchstat` сравнивает среднее время запроса каждого прогона. Эти числа не подменяют p95 из параллельного сценария.
- Планы `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` сохраняются для custom/generic plan по реальному SQL приложения. Глубокий курсор соответствует 90-му процентилю допустимой области; setup вычисляет якорь, API не получает OFFSET.
- После записей сверяются остатки с журналом, активные резервы с балансами и строками документа, завершённость операций, наличие аудита/outbox. Для одинаковых ID проверяется отсутствие двойного резерва.

Нагрузочный regression `TestLoadPageWorkStaysBounded` ограничивает суммарные обращения к shared blocks для страницы, а не миллисекунды. Он не зависит от скорости конкретного CPU и выявляет повторный просмотр истории.

## Воспроизведение

Требуются PostgreSQL 17 с `pg_stat_statements`, Go из `go.mod`, PowerShell и свободное место для исходной БД и двух её копий. Измерения запускаются последовательно. Для race-проверок нужен C-компилятор; race detector не включается в измеряемые бенчмарки.

```powershell
$common = @{
  PgBin = 'C:/Program Files/PostgreSQL/17/bin'
  GoExe = 'C:/path/to/go.exe'
  Session = 'work/load-session.json'
}
try {
  ./scripts/test-load.ps1 @common -Mode Setup
  if ($LASTEXITCODE) { throw 'Setup failed' }
  ./scripts/test-load.ps1 @common -Mode Measure -Label baseline -BaselineRef e0ab625 -Seconds 3 -Repetitions 3
  if ($LASTEXITCODE) { throw 'Baseline failed' }
  ./scripts/test-load.ps1 @common -Mode Measure -Label optimized -OptimizeSchema -Seconds 3 -Repetitions 3
  if ($LASTEXITCODE) { throw 'Optimized run failed' }
} finally {
  ./scripts/test-load.ps1 @common -Mode Stop
}
```

Session-файл содержит путь к сохранённому стенду; результаты находятся в его `Root`, подпапках `baseline`/`optimized`. Секреты и токены в результаты не записываются. `BaselineRef` накладывает прежний `store.go` на текущий нагрузочный harness; остальные компоненты API/OIDC/guards неизменны. `OptimizeSchema` применяет новую миграцию индексов только к копии фазы.

Теги нагрузки отделены от обычной проверки: `go test -tags=integration,load ./internal/postgres ...`. Не запускайте все load-тесты одним `-run .`: сначала требуется отдельная стадия Setup. Для короткой проверки harness можно задать меньшие количества, но на каждый scope должно приходиться больше 50 строк для курсора.

Измеренный результат конкретного стенда и сырьё сравнения сохраняются в `docs/verification/load/`; он не является SLA или результатом длительного испытания production-развёртывания.
